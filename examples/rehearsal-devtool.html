Three steps, none of which touch production

01

It takes a copy of the queries you actually run

From pg_stat_statements or a log export — statement shapes and their frequency, not the values in them. Parameters are stripped before anything leaves your infrastructure.

02

It builds the schema your branch would produce

Migrations in the pull request are applied to an empty database in a container. Nothing is applied anywhere else, and the container is discarded when the check finishes.

03

It plans every statement against that schema

Each statement is prepared, not executed. A statement that no longer plans is reported with the object that removed it and the migration line that did it. No rows are read and no rows are written.

It only knows the queries you have already run.

A statement that has never appeared in the log is invisible to Rehearsal — a rarely used report, a code path behind a flag, a query built at runtime from user input. This is the tool's real boundary, and it is the first thing worth knowing about it. It catches what production actually does, not everything the code could do.

Run it on one pull request

Add the check to a repository, point it at a query-log export, and open a PR that touches the schema. If it finds nothing, you have lost one CI minute.

$ rehearsal check --migrations db/migrate --log queries.json
