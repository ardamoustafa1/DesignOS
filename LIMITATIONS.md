# Limitations — What DesignOS Is Not (Yet)

Every module in this project demands a state matrix, an instant-fail sweep, and honest
labeling of what wasn't checked before anything ships (`checklists/pre-flight.md`,
`brain/quality-bar.md`). Holding the project itself to a lower standard than its own
output would be the least credible thing it could do
(`psychology/trust.md` — the ledger applies to us too). This file is that sweep.

## 1. The eval results are a maintainer self-test, not independent proof

Both arms of `evals/RESULTS.md`'s Run 001 were authored by the same person who wrote the
rules being tested — the "control" page's flaws were written deliberately, not produced
by an unprompted agent under real conditions. That demonstrates the *validators* fire
correctly. It does not demonstrate that DesignOS reliably changes an *independent* agent's
output on a brief it wasn't tuned for. Run 002 — the slot that would actually support the
claim — is open and empty. **Until someone else fills it, treat every "measured" claim in
this README as a hypothesis with working instrumentation, not a proven result.**

## 2. The showcase is self-authored, not field-tested

All four pages in `examples/` and the website itself were built by the maintainer
applying the rules to a fictional product invented for the purpose. They prove the system
is *internally coherent* — the rules don't contradict each other when followed carefully.
They do not prove the rules survive contact with a real client's ambiguous brief, a real
existing codebase's constraints, or a real deadline. `evals/field-report-001.md` is the
first attempt at closing this gap (a structural stress-test that found and fixed a real
coverage hole — RTL/i18n layout was almost entirely missing before that audit). It is one
data point, self-conducted, not a track record.

## 3. Scale outran field-testing

180+ files of specific, opinionated rules (4px grids, 95-point thresholds, named
compositions) were written in a concentrated burst, not accumulated from years of
real projects hitting real edge cases. Some rules will turn out too rigid for a real
brand's constraints, some will contradict each other in combinations not yet tried, and
some sector files will have gaps like the RTL one until someone with real domain
experience in that sector reads them critically. `CONTRIBUTING.md`'s rule-challenge
process exists specifically for this — it hasn't been exercised by anyone outside the
project yet.

## 4. Zero external validation as of this writing

No independent contributors, no third-party showcase entries, no field reports from
outside the maintainer, no production usage the maintainer can point to. The
comprehensiveness is real; the track record is not yet. A reader should weight this
project's claims accordingly until that changes — and it can only change through real
external use, which this document is explicitly inviting rather than obscuring.

The 36-rule child-process ledger is labeled `isolatedRuleEval`, not independent or
external evaluation. `externalEval` remains `false` in the capability registry until a
third-party run satisfies the evaluator, blind-protocol, immutable-evidence, and
rule-result contract in `evals/external/registry.json`.

Native evidence is tracked per platform and per tier
(`capabilities/native-evidence.js`: `source-conformance` → `simulator-smoke` →
`platform-verified` → `real-device-verified`), not as one blanket claim — a single
passing CI run on one stack must never silently promote the other three. The claim
above is generated straight from `evals/native-device/registry.json`, which starts
empty and is only ever appended to by `.github/workflows/promote-native-evidence.yml`
opening a reviewed PR after `native-smoke.yml` passes on `main` — never hand-edited.
`.github/workflows/native-smoke.yml` builds, installs, launches, and screenshots
`starter/mobile-app` (the `react-native` stack) on both an iOS Simulator and an Android
Emulator; once that evidence is promoted it earns `react-native` the `simulator-smoke`
tier specifically, not "device-verified" generally. `swiftui`, `compose`, and `flutter`
have no CI of any kind yet — they remain `source-conformance`: shared physics
execution, capability contract checks, iOS Swift type-checking and Flutter analysis
when those SDKs are present, plus portable Swift/Dart/TSX parsing fallbacks. Even at
its best, `simulator-smoke` does not claim device-level frame, haptic, keyboard,
Dynamic Type, or TalkBack/VoiceOver proof; that's `platform-verified` and
`real-device-verified` territory, and no platform has reached either yet.

## 5. Translations are unreviewed

The seven non-English READMEs are LLM-authored in a single pass with no native-speaker
review. Treat them as a starting point for that language's community, not as
authoritative — corrections are one of the highest-value contributions available right
now (`CONTRIBUTING.md`).

## 6. The routing table's coverage is asserted, not exhaustively tested

The kernel (`CLAUDE.md`) routes task signals to modules via a large table. It has been
checked for internal consistency (`validators/check-refs.sh` verifies every cross-
reference resolves to a real file) but not exhaustively tested for *completeness* — i.e.,
whether every realistic brief actually finds the module it needs. Finding #2 in the field
report (modules missing cross-references to a newly-added file) is the exact failure mode
to expect more of: a module can exist and still be effectively invisible to routing.

## 7. The reference artifacts meet the Ceiling Contract; the advisories are open

`CLAUDE.md` §4.5 originally landed after the artifacts were built, and the sweep found 16
violations. Those are closed. `npm run audit:ceiling` now reports:

| Target | Violations | Advisories |
|---|---:|---:|
| `goldens/` | 0 | 12 |
| `website/` | 0 | 6 |
| `examples/` | 0 | 10 |
| `systems/` | 0 | 0 |

What closing them involved, and what it did not: the goldens gained named typefaces, a
declared light model, a three-level tinted elevation stack, grain, and a second container
width; `website/` had seven pure-black shadows tinted, with the deliberate anti-pattern
exhibit in `before-after.html` opted out with a stated reason rather than "fixed". Golden
pixel-diff evidence was regenerated (`npm run update:goldens`) and the suite verifies clean.

**§4.5 now has a seventh requirement: one memorable moment**, closing either the material
route (an inspectable artifact — table, code block, chart, framed screenshot) or the motion
route (evidence of a licensed signature technique), never both, and never mandating motion
specifically — `brain/wow-calibration.md` §1 ranks motion fourth of four routes, after
composition, material, and voice, and a checker that forced motion on every page would
contradict the module it is meant to enforce. `ceiling-no-memorable-moment` reuses
`validators/signature-fingerprints.js`'s eleven named techniques plus three broader
mechanism patterns (border-beam, pointer-follow, sticky scroll-rail) so a hand-rolled
signature is recognized by its shape, not by matching motion/signature-moments.md's sample
function names verbatim. Verified independently in both directions:
`examples/rehearsal-devtool.html` (material-only, a real `<table>`, no JS signature) and
`examples/editorial-portfolio.html` (motion-only, a pointer-follow plate, no table) both stay
clean — the rule accepts either route alone by design, asserted in
`validators/test-craft-ceiling.js`.

**The 28 remaining advisories are real and open.** Mostly `ceiling-no-arrival`,
`ceiling-uniform-rhythm`, and `ceiling-single-container` on surfaces that genuinely have
none — the flat documentation pages under `website/` and the dashboard and docs goldens,
where an arrival is arguably wrong anyway (`motion/arrival.md` forbids it on app surfaces) —
plus a handful of new `ceiling-no-memorable-moment` hits (`examples/index.html`, a listing
page; `examples/showcase-relay-pricing.html`, which has no comparison table). Each needs a
per-surface judgment, not a sweep, which is why `npm run validate:ceiling` gates on
violations and prints advisories rather than failing on them.

Three fixes in this pass were to the checker, not the artifacts, and all three were false
negatives that would have let real flatness through: `--shadow-rgb: 4 6 12` parsed as a
single-layer cast shadow (reporting the flattest possible verdict on files whose elevation
is correct); `#100D0A` did not match `rgb(16 13 10 / .72)` as the same palette entry; and
`process.exit()` immediately after a large `--json` write truncated the payload past the
64KB pipe buffer in three validators (`check-system-integrity`, `check-system-conformance`,
`check-craft-ceiling`) — silent corruption for anything piping their output.

## 8. 151 of the 152 design systems are imported, and 62% of them contradict themselves

`systems/` ships 153 packages. Exactly **one** (`kiln`) was authored for DesignOS. The rest
are imported from nexu-io/open-design's catalog and upgraded on import — see `systems/NOTICE`
for the licence and the modification list.

**The measured defect.** `npm run audit:systems` diffs the colours each package names in its
prose against the values in its own `tokens.css`:

```
150 packages judged · 140 over the 20% threshold
1203/1925 colours named in prose (62%) do not exist in the token layer
```

Twenty-five packages disagree with themselves completely. `atelier-zero`'s prose specifies
warm ivory paper `#efe7d2` with a coral accent `#ed6f5c`, under the sentence "All values are
tokens. Do not invent new hex" — above a token file that reads pure white with a black
accent. An agent handed the prose and an agent handed the tokens build different pages, and
neither is wrong by its own lights. `kiln` is at 0%; four packages are.

This is inherited, not introduced — the importer copies prose and tokens faithfully and does
not reconcile them, because which half is stale is the package author's call and not a
checker's. `systems/README.md` states the rule (tokens win). The checker exists so the
disagreement is at least visible; it does not fix it, and until a package is reconciled by
hand its prose should be read as commentary rather than contract.

**What the catalog still does not buy:**

1. **Field evidence.** Nobody has built a real product with any of these packages. The
   `accent.maxSolidFills` budgets in generated `lint.json` files are the importer's
   conservative defaults, marked untested in each file. This is limitation #3 repeating
   itself with nicer folders.
2. **Composition.** Two of the seven Ceiling Contract requirements — section rhythm and
   optical corrections — are page decisions, not token values, and cannot be imported. A
   conforming token layer does not make a page premium; the generated fixtures demonstrate
   the token layer only, deliberately.
3. **Originality.** A package derived from a real company's public design language produces
   competent imitation, which is what `brain/originality.md` spends its whole length arguing
   against. The swap test fails by construction on most of the catalog.

## What would change these ratings

- An independent Run 002 in `evals/RESULTS.md`, positive or negative
- Real third-party entries in `SHOWCASE.md` — actual products, actual friction reports
- Rule-challenge issues from people who hit a contradiction or a bad fit
- Native-speaker review of any translated README
- More field reports in `evals/field-report-*.md` — self-conducted ones from the
  maintainer are welcome too; more audits finding more real gaps is the system working
  as designed, not a sign it's failing

This file gets edited as those things happen — a limitation that's been resolved should
be struck through with the fix linked, not silently deleted (`memory/README.md`'s
"supersede, don't delete" rule, applied to the project's own record).
